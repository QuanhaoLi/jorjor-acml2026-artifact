
# k.9.0 Exact 169-Way Poker Posterior Audit

## Purpose

Replace the weak binary range-label proxy with a proper-distribution audit of
the exact 169-way opponent posterior under the known teacher data generator.

## Exact Conditioning Contract

For every full-input train, validation, and test decision, the oracle computes:

```text
P(opponent physical combo and 169 class |
  own cards, current board, actor/street/legal set, past actions;
  uniform deck, frozen deterministic heuristic teacher)
```

It enumerates 1,326 physical two-card combinations, applies exact card removal,
filters combinations by every previously observed target-player teacher action,
and aggregates surviving combinations into canonical `HAND_169_LABELS` order.
It excludes data RNG state, hand id, actual opponent cards, future board,
current action, and terminal return.

The readout uses the original unmasked checkpoint forward and locked
`encoder_layer_2`. A/V rows retain current action and terminal return only as
explicit target-side nuisance controls; they are not posterior conditioning
variables.

## Product Protocol

- Fresh k.8.0 checkpoints: seed k/l/m/n/o.
- Source revision: `e2e4821a1bf02f962426dea4616feffbc84baea0`.
- All learned rows use an exact card-removal log-prior offset plus one linear
  169-way correction.
- Six rows: hidden, target-side A/V, 30-d composition, A/V+composition,
  A/V+composition-residual hidden, and nested A/V+composition+residual hidden.
- Required controls: uniform, exact card-removal prior, identity `q=b`.
- Maximum 30 epochs, validation soft-CE selection, patience 5, batch 512.
- Test metrics: CE, KL, JS in nats and class-summed Brier.
- Point uncertainty: 10,000 equal-hand cluster bootstrap draws.
- Pair uncertainty: 10,000 dyadic hand-node bootstrap draws.
- Across runs: equal-run Student-t interval, df=4.

Remote environment:

```text
Python 3.12.3
PyTorch 2.4.1+cu121
NumPy 2.1.3
Tesla V100-PCIE-16GB, physical GPU3 only
```

Full run time was about 20 minutes, from `11:51:35` to `12:11:47` UTC+8.

## Oracle Validation

- Exact trajectory/card/action invariants passed on every split and run.
- Realized opponent physical combo retained nonzero support at every point.
- Identity oracle has KL/JS/Brier approximately zero.
- Identity matched-pair MAE is zero and Pearson/Spearman/slope are one.
- 50,000-hand oracle generation takes about 15 seconds and uses compact
  uint16 counts plus float32 posterior arrays.

## Support-Contract Repair

The original feasibility rule required at least 100 buckets and 2,000 pairs,
while the frozen key has exactly 30 buckets and the 64-pair cap makes 1,920 the
design maximum. The raw k.9.0 product therefore correctly records its original
`insufficient_support` label but cannot be interpreted under that impossible
contract.

k.9.0.1 changes only feasibility to at least 20 buckets, 1,500 nonzero pairs,
and 1,000 hand nodes. No posterior, weight, score, pair, or interval changes.
All five runs pass repaired support and receive:

```text
mixed_exact_posterior_evidence
```

## Scientific Interpretation

Exact known-teacher posterior information is linearly recoverable beyond the
declared A/V+composition controls under average proper scores. However, this
increment does not translate into calibrated matched-composition posterior
movement: pair-JS magnitude is strongly underpredicted and the MAE analysis does
not establish a reliable improvement over A/V+composition.

Allowed:

```text
The frozen full-input layer contains a small, reproducible, metric-specific
increment in exact known-teacher posterior information beyond the specified
controls, but does not establish calibrated matched-pair posterior tracking.
```

Forbidden:

```text
The model maintains a Bayesian belief state.
The hidden representation tracks posterior updates faithfully.
The posterior information causally drives behavior.
The result transfers to unknown opponents.
```
